# 截图附件本机验证 · 2026-10-31

环境：Fedora 45，Niri 26.04（运行中），Rust 1.98.1，Node 24.22.1，pnpm 11.25.0。本次没有读取或上传用户的真实屏幕内容；原生合成测试使用假 `niri` 和 64×48 合成 PNG。

## 1. 接口核对

| 检查 | 证据 | 结论 |
| --- | --- | --- |
| Niri 截图动作 | `niri msg action screenshot --help` 提供 `--path <PATH>`、`--show-pointer` | 可用；路径必须是绝对路径 |
| 其他截图动作 | `screenshot-screen`、`screenshot-window` 也存在，但本单元使用交互区域截图 | 不选全屏/单窗口作为默认入口 |
| 事件协议 | 二进制约 26.04 含 `Event::ScreenshotCaptured`（单元素结构）与字段 `path`；解析器只接受字符串 path | 事件只作为提示，文件轮询与 PNG 校验才是成功依据 |
| 命令完成语义 | 2026-10-29 原型：命令约 62–69ms 返回；此前已记录“退出成功≠图片已保存” | 不把退出码当保存成功 |
| Esc 取消 | 2026-10-29 用户确认取消后 60 秒无新文件；本次没有再次操作真实截图 UI | Niri 的 Esc 取消仍无可靠事件；本实现不以“静默”推断取消 |
| Portal | 2026-10-29：interactive 返回 response=2，缺 InteractiveScreenshot | 仍不作为默认后端 |

本次没有对真实屏幕触发 `niri msg action screenshot`，因此“真实 Niri 交互截图、真实 Esc 取消、真实多屏”仍未验收；不能拿假 `niri` 结果替代。

## 2. 本单元实现边界

- 新入口 `zwen screenshot`（兼容 `capture-screenshot`）；胶囊内也提供截图按钮。未安装 Niri 全局快捷键，仍需用户自行绑定。
- 每次捕获生成 32 位十六进制 request ID 和唯一绝对路径 `<data>/attachments/incoming/<id>.png`。先订阅 `niri msg event-stream`，再调用 `niri msg action screenshot --show-pointer false --path <path>`。
- 成功判定：命令退出成功 + 唯一路径文件存在且大小稳定 250ms + PNG 头/尺寸/解码校验通过。命令成功但无文件不算成功。
- 取消：胶囊内“取消等待”或再次触发 `screenshot` 会标记当前请求取消；若 Niri 之后仍保存了该路径，文件会被删除，绝不附加。Niri 的 Esc 取消无法实时感知，最迟由 60 秒超时结束等待。
- 超时：默认 60 秒；超时后不附加，显示“等待截图超时”。迟到文件只可能被清理，不会被识别为新请求。
- 归属：事件/文件只与当前 request ID 的路径匹配；旧请求的迟到结果路径不同，不能附加到新草稿。新请求开始前会删除 `incoming` 中所有 32-hex 请求文件（它们不可能再被确认）。
- 窗口意图：请求开始时取得 intent；结束时只有没有更新 intent 才重新激活，用户后来的收起/展开不被迟到结果覆盖。~~截图期间胶囊保持可见~~（2026-11-01 依用户真实反馈修改：可见窗口会遮挡并污染待截图区域，已改为**等待选区期间隐藏本应用窗口**，结束后经 intent 重新显示）。取消语义 2026-11-01 再修：Niri 的 Esc 无事件、旧等待最长挂 60 秒，**等待期间再次触发=丢弃旧等待并重新开始截图**（不再仅弹胶囊）；若 Niri 截图界面仍开着就重按，新动作可能被忽略，最迟 60 秒超时提示。
- 图片边界：仅 PNG；单张压缩≤24MiB；宽高≤8192 且总像素≤10,000,000；最多 3 张、合计≤48MiB；生成最长边≤480 的缩略图；原图/缩略图 0600，目录 0700。超限或解码失败删除临时请求文件并提示，不覆盖旧附件。
- 存储：独立 `attachment.sqlite3` schema 1，不改动草稿/配置/聊天三个库；重截在同一事务内替换旧记录，失败保留旧附件。
- 发送闸门：视觉模型尚未接入，存在截图附件时发送按钮禁用，Ctrl+Enter 也会被拦截并提示；不会把图片或“文件名”发给当前文字模型。
- 未上传：图片只写入本机数据目录，不进入聊天、日志或模型请求。
